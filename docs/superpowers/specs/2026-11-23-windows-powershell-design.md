# Windows PowerShell 支持设计

## 意图

让 `pi -ps coding` 在原生 Windows 的 PowerShell 里也能用：`npm run setup` 把 `pi` 包装函数写进 PowerShell profile，`npm run teardown` 干净地摘掉它。此前两份设计（`2026-11-20-preset-cli-design.md`、`2026-11-21-teardown-and-dry-run-design.md`）都把「不支持 Windows/PowerShell」写成非目标，本设计改动那条决定。

## 相关现状

- `src/shell-integration.ts` 是唯一的 shell 知识集中点：`SUPPORTED_SHELLS`（fish/bash/zsh）、`renderFunctionSource`、`shellIntegrationPaths`、`installShellIntegration`、`removeShellIntegration`、`renderShortcutHint`。
- POSIX 形态是「写 `$XDG_CONFIG_HOME/pi-presets/pi.sh` + 在 `.bashrc`/`.zshrc` 插受管标记块 dot-source」；fish 形态是单个 `conf.d/pi-presets.fish`。
- `setup.ts` 用 `basename($SHELL)` 猜 shell，用 `$XDG_CONFIG_HOME` 算路径；`teardown.ts` 缺省对全部受支持 shell 卸载。
- `src/cli.ts` 的 `findRealPi` 只在 `PATH` 里找名为 `pi` 的文件并检查 `X_OK`，然后 `spawn(realPi, args, {shell:false})`。
- `src/install-presets.ts`（`postinstall`）`spawn('npm', ...)`。

Pi 在 Windows 上的安装形态（`install.ps1` 与 npm 的行为）：

- npm 与 managed 安装都生成 `pi.cmd`、`pi.ps1`，managed 安装还多一个 `pi`（POSIX sh 脚本）和 `pi-launcher.js`。
- Windows PowerShell 的 profile 是 `Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1`，PowerShell 7 是 `Documents\PowerShell\Microsoft.PowerShell_profile.ps1`；`Documents` 可能被 OneDrive 重定向到 `OneDrive\Documents`。
- `npm run` 在 Windows 上由 `cmd.exe` 执行 script（npm 默认 script-shell），所以 `setup` 进程的父进程是 cmd，不是 PowerShell。

## 目标

- Windows 上 `npm run setup` 把 `pi` 函数写进本机**所有被找到的** PowerShell 宿主的 profile 受管块，`npm run teardown` 能把它们摘干净。
- 平台门禁：Windows 只接受 `powershell`；Linux/macOS 只接受 fish/bash/zsh，`--shell powershell` 报用法错误退出码 2。
- `--dry-run` 在 Windows 上输出可直接 `Invoke-Expression` 的函数定义，stdout 里没有别的字节。
- Windows 上 `pi -ps coding` 能真正启动**真实** pi（`pi.cmd`），参数、退出码、当前目录、stdin/stdout 透传。
- Windows 上 `npm install` 的 `postinstall` 能跑起来（`install-presets.ts` 不再直接 `spawn('npm')`）。
- 现有 POSIX/fish 行为与测试不变。

## 非目标与反目标

- 不支持 Linux/macOS 上的 pwsh（明确按平台门禁拒绝，而不是"能跑但没人测"）。
- 不探测「用户当前在 pwsh 7 还是 5.1 里敲命令」：`npm run` 的父进程恒为 cmd，要判定得查父链的 CIM，代价与收益不成比例；两个宿主都会写，探测与否不影响写入目标。
- 不写 `profile.ps1`（CurrentUserAllHosts），只写 `$PROFILE`（CurrentUserCurrentHost）。
- 不改 Pi 本身，不接管 Pi 的更新/安装流程。
- 不追求把 PowerShell 变成通用启动器：`pi` 函数只做参数透传。

## 约束

- `setup` 是子进程，不能修改父 shell；「只改当前 shell」仍靠 stdout + `Invoke-Expression`。
- profile 路径不可靠推算（OneDrive 重定向、自定义 profile），必须问宿主。
- Windows 上不能 `spawn` 一个 `.cmd`（Node 18.20+/20.12+ 直接 `EINVAL`），必须经 `cmd.exe`。
- 仓库可能被克隆到含空格、引号、非 ASCII 字符的路径。
- 测试在 Linux 上跑：Windows 专属逻辑必须可通过注入平台、环境与宿主查询函数来测。

## 方案比较

### profile 路径怎么定

1. **启动宿主问 `$PROFILE`（已选择）**：按 `pwsh.exe` on PATH → `%ProgramFiles%\PowerShell\7\pwsh.exe` → `powershell.exe` on PATH → `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` 找宿主，用 `-NoProfile -NonInteractive -Command '...; $PROFILE'` 取回准确路径。优点：重定向与自定义 profile 都不会写歪，同时天然得到「哪些宿主装了」。代价：安装时多一两个子进程。
2. **按 `%USERPROFILE%\Documents\...` 推算**：零子进程、纯函数、最好测。代价：OneDrive 重定向即写错，且会为没装的宿主凭空建 profile。
3. **推算 + 能启动宿主时用其返回覆盖**：覆盖两种失败模式，但两条代码路径都要维护，行为随机器不同。

选 1：这套东西的价值就是「装一次就准」，省两个子进程换不来；且它能用假宿主在 Linux 上完整测到。

### Windows 上怎么启动真实 pi

1. **PATHEXT 感知解析 + `.cmd` 经 `cmd.exe /d /s /c`（已选择）**：`findRealPi` 在 `win32` 上按 `pi.exe` → `pi.cmd` → `pi.bat` 找文件（**跳过无扩展名的 `pi`**，它是 sh 脚本，在 Windows 上 spawn 必失败）；`.exe` 直接 `spawn`，`.cmd`/`.bat` 经 `cmd.exe` 传单条命令行。
2. **解析 `pi.cmd` 内容，直接 `node` 它指向的 JS**：能绕开 cmd 的引用问题，但依赖 shim 内部结构（npm 与 managed 安装的写法未来可能变），脆弱。
3. **在 PowerShell 函数里用 `Get-Command pi -CommandType Application` 取真实命令再调用**：函数里拿到的仍是 shim 路径，参数展开（`-ps`）仍要回到 `cli.ts`，等于多一层而没解决问题。

选 1：与现实一致，且引用规则可以写成纯函数单独测。

## 实现组成

### `src/shell-integration.ts`

- `supportedShells(platform: NodeJS.Platform): readonly SupportedShell[]`：`win32` → `['powershell']`；其余 → `['fish', 'bash', 'zsh']`。`isSupportedShell(value, platform)` 基于它。`SUPPORTED_SHELLS` 保留为 POSIX 集合或删除（实现细节）。
- `renderFunctionSource('powershell', repoRoot)`：

  ```powershell
  # Generated by pi-presets setup.
  function pi {
      & node '<cliPath>' @args
  }
  ```

  单引号字符串按 PowerShell 规则转义（`'` → `''`）。
- `renderShortcutHint('powershell')`：`function picode { pi -ps coding @args }`（`Set-Alias` 不能带参数，所以用函数）。
- `installShellIntegration`：`powershell` 不起作用（该函数的 `shell` 参数收窄为 `Exclude<SupportedShell, 'powershell'>`）。PowerShell 的安装/卸载由 `src/powershell-profile.ts` 的批量函数负责：`installPowerShellProfiles({profilePaths, repoRoot})` / `removePowerShellProfiles({profilePaths})`，先全部读取并校验、全部通过后才写（跨文件两阶段校验用单文件 API 做不到）。
- `removeShellIntegration`：同理只管 fish 与 posix；PowerShell 的候选路径扫描在 `teardown.ts` 里调批量函数。

### 宿主发现（新模块 `src/powershell-host.ts`）

```ts
export interface PowerShellHost {
  kind: 'pwsh' | 'windows-powershell';
  executable: string;
  profilePath: string;
}
export interface DiscoverOptions {
  platform: NodeJS.Platform;
  env: NodeJS.ProcessEnv;
  pathValue: string;
  query?: (executable: string, args: string[]) => string; // 默认 spawnSync
}
export function discoverPowerShellHosts(options: DiscoverOptions): PowerShellHost[];
```

- 候选按 Pi 自己的顺序：`pwsh.exe`（PATH）→ `%ProgramFiles%\PowerShell\7\pwsh.exe` → `powershell.exe`（PATH）→ `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`。
- 查询命令：`-NoProfile -NonInteractive -Command '[Console]::OutputEncoding=[System.Text.Encoding]::UTF8; Write-Output $PROFILE'`，stdout 按 UTF-8 解码后 `trim()`。失败、超时（10s）、空输出都算该宿主的查询错误。
- 两个宿主都存在就都返回。
- **部分失败的语义（我的判断）**：
  - `setup`：任何一个「找到但查询失败」的宿主都让整次安装**中止**（退出码 1，一个文件都不写，与现有「畸形标记整体中止」的取向一致），错误信息带上宿主路径与原因。宁可不装，也不要装一半让人以为生效了。
  - `teardown`：查询失败**不阻断卸载**，降级为只用推算候选路径扫描，并在 stderr 说明「宿主 X 查询失败，已退回路径扫描」。卸载不能因为一台坏宿主而永远清不掉。
  - 因此 `discoverPowerShellHosts` 返回 `{ hosts, failures }`，由两个入口各自决定怎么对待。

### 平台门禁

- 平台取值读 `process.platform`，测试可用环境变量 `PI_PRESETS_PLATFORM` 覆盖（仅供测试与 CI 的缝隙，在 README 里注明）。
- `setup --shell powershell` 在非 Windows：`Unsupported shell on this platform: powershell. Choose fish, bash, or zsh.`，退出码 2。
- `teardown` 不带 `--shell`：卸载当前平台的全部受支持 shell。
- 用法错误时的文案随平台变化（列出该平台可选项）。

### profile 受管块

```
# >>> pi-presets >>>
# Generated by pi-presets setup.
function pi {
    & node 'C:\path\to\src\cli.ts' @args
}
# <<< pi-presets <<<
```

- 沿用现有标记与「追加时前面留一个空行、块后一个换行」的约定，`locateManagedBlock` / `updateRc` / `stripManagedBlock` 复用，因此「安装后卸载逐字节回到安装前」的不变量同样成立。
- 换行：新建 profile 用 CRLF；向已有文件追加块时也用 CRLF（PowerShell 两种都接受，用 CRLF 与 Windows 习惯一致）。
- 编码（profile 一律按 Buffer 读、按探测结果决定，不能盲读 `'utf8'`）：
  - 无 BOM：按 UTF-8 处理（现状），内容原样写回。
  - UTF-8 BOM：保留 BOM 原样写回，不额外添加。
  - **无 BOM 但生成的函数含非 ASCII 字符（例如仓库路径带中文）时，写入前置 UTF-8 BOM**：否则 5.1 按 ANSI 解码，函数里的非 ASCII 路径会直接失效。代价是卸载后可能留下 3 字节 BOM（记入已知限制）。
  - **UTF-16LE/BE BOM：中止**（退出码 1，不写任何文件），提示把 profile 另存为 UTF-8。理由：5.1 的 `>`/`Out-File` 默认写 UTF-16LE，盲读 utf8 会把 `\0` 夹进内容，标记定位失败后当成「无块」追加，用户原有配置会被整体写成乱码。
  - 新建文件写 **UTF-8 with BOM**（5.1 无 BOM 时按 ANSI 解码，路径含中文会乱码）。
- 读取与编码探测抽成一个函数，`install` 与 `remove` 共用；`remove` 遇到 UTF-16 同样中止（此时文件里不可能有我们写的块，中止是为了不误伤）。
- 标记块内不写任何依赖 `$PSScriptRoot` 或相对路径的东西。

### `setup` 输出与 `--dry-run`

- install 成功：列出写入的 profile 路径；`shell === 'powershell'` 时提示 `Restart PowerShell or run: . $PROFILE`（两个宿主都写时两行都提示）。
- `--dry-run`：stdout 恰好是 `renderFunctionSource('powershell', repoRoot)`（不含标记），stderr 打印「不会写盘」「将写入：<路径列表>」；TTY 时额外打印（**编码必须先摆好**：Node 写的是 UTF-8 字节，PowerShell 侧按当前代码页解码，仓库路径含中文时函数里的路径会乱码）：

  ```
  [Console]::OutputEncoding = [Text.Encoding]::UTF8; $OutputEncoding = [Text.Encoding]::UTF8; Invoke-Expression (& npm.cmd run --silent setup -- --dry-run --shell powershell | Out-String)
  ```

  README 里提供同一段，并注明编码要先设。

- 一个宿主都没找到（`--dry-run` 也一样）：报错退出码 1，信息里给出搜索过的四个位置并提示先装 PowerShell 7 或确认 `--shell`。

### `teardown` 的候选 profile 路径

卸载时宿主可能已经被删掉，所以候选路径 = 宿主报告的路径 ∪ 推算路径：

- `%USERPROFILE%\Documents\PowerShell\Microsoft.PowerShell_profile.ps1`
- `%USERPROFILE%\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1`
- `%OneDrive%\Documents\PowerShell\Microsoft.PowerShell_profile.ps1`（`OneDrive` 存在时）
- `%OneDrive%\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1`（同上）

只有确实含受管标记的文件才被改写，因此多扫几个候选不会碰到用户内容。畸形标记仍整体中止（退出码 1，不写任何文件）。

### `src/cli.ts` 的 Windows 启动

- `findRealPi({ pathValue, platform, pathExt })`：
  - 非 win32：沿用现状（`pi` + `X_OK`）。
  - win32：`pathExt` 取 `env.PATHEXT`（缺省 `.COM;.EXE;.BAT;.CMD`），**PATHEXT 顺序即权威**；按 PATH 顺序、每个目录按 PATHEXT 顺序试 `pi<ext>`，取第一个 `isFile()`。不试无扩展名的 `pi`（那是 sh 脚本）。找不到则报错并提示 `pi` 不在 PATH 上。
  - 启动形态由扩展名决定：`.exe`/`.com` 直接 `spawn`；`.cmd`/`.bat` 经 `cmd.exe`。
- `spawn` 形态：
  - `.exe`：`spawn(exe, args, {shell:false, stdio:'inherit'})`。
  - `.cmd`/`.bat`：`spawn(process.env.ComSpec ?? 'cmd.exe', ['/d','/s','/c', commandLine], {windowsVerbatimArguments:true, stdio:'inherit'})`，`commandLine` 为 `"<exe>" <quoted args...>` 并在最外层再包一层引号交给 `/s` 剥掉。
- 引用规则（新导出 `quoteForCmd(arg)`，纯函数、可单测）：
  - 空串 → `""`。
  - 含空格/制表符/`"` → 用 `"` 包起来，内部 `"` 与尾部反斜杠按 MSVCRT 规则转义（`\` 加倍后接 `\"`）。
  - 不含引号且不含空白时，`& | < > ^ ( )` 前加 `^`。
  - 已被引号包起来的内容里 `& | < > ^ ( )` 是惰性的，不再加 `^`。
  - **含 `"` 的参数在 `.cmd` 路径上直接拒绝**（报错退出码 1）：MSVCRT 的 `\"` 在 cmd.exe 眼里不是转义，而是关闭我们加的引号，后面的 `&`/`|` 会变成真正的命令分隔符——这是可执行任意命令的口子。不承诺 cmd 层面的引用安全，宁可不启动也不拼一条可能跑起别的命令的命令行。`.exe` 直启不受影响。
  - 已知限制：`%`（cmd 会展开 `%VAR%`）与 `!`（仅在启用延迟展开时特殊）无法在不破坏内容的前提下转义，按原样传递。写进 README 的已知限制。

生成的函数体在两个宿主上的传参差异（`$PSNativeCommandArgumentPassing`）：Windows PowerShell 5.1 是 `Legacy`，PowerShell 7.3+ 在 Windows 上默认 `Standard`，含内嵌引号或以 `\` 结尾的参数在 5.1 上会走样。我的判断是**接受差异并写进已知限制**，不往函数体里塞 `$PSNativeCommandArgumentPassing`：该变量在 5.1 上不存在、设了也没用，塞进去只会让 dry-run 输出与 profile 块的同源性更难讲清楚。真实冒烟必须两个宿主都过一遍。
- 信号处理保持现状（Windows 上 `SIGTERM`/`SIGHUP` 语义不同，但注册与转发不会报错）；不加平台分支。

### `src/install-presets.ts`

`postinstall` 里不再 `spawn('npm', ...)`：

- `process.env.npm_execpath` 存在（npm 生命周期脚本里总是存在）→ `spawn(process.execPath, [npmExecPath, command], ...)`。
- 否则 win32 → `spawn(ComSpec, ['/d','/s','/c', `npm ${command}`], ...)`；其他平台 → 现状 `spawn('npm', [command])`。

### README

- Setup 章节：说明支持的 shell 随平台不同；Windows 上 `npm run setup` 会写所有找到的 PowerShell 宿主的 profile，`--shell powershell` 可显式指定；`exec "$SHELL"` 换成 `. $PROFILE` 的说明。
- `--dry-run` 的 PowerShell 写法。
- 简写建议：`function picode { pi -ps coding @args }`。
- 已知限制：`%`/`!` 参数、非 Windows 不支持 pwsh、`Set-Alias pi` 会遮蔽函数。

## 已知限制

- 参数含 `%VAR%` 或 `!` 时，经 `cmd.exe` 转发会被 cmd 改写（见引用规则）。
- 参数含 `"` 时，经 `pi.cmd` 启动会被拒绝（退出码 1）：cmd.exe 的引号语义使无法在转发时保证不出现命令注入。`.exe` 直启不受影响。
- 向无 BOM 的既有 profile 写入非 ASCII 函数时会补一个 UTF-8 BOM；卸载后可能留下 3 字节 BOM。
- 用户若用 `Set-Alias pi ...`，别名优先级高于函数，会遮蔽包装器。
- 已存在的 profile 无 BOM 且是 ANSI 编码、又含非 ASCII 内容时，写回会让那部分内容坏掉（UTF-16 已被 BOM 探测挡住）。
- 5.1 与 7 对 `& node ... @args` 的实参重组规则不同，含内嵌引号或以 `\` 结尾的参数在 5.1 上会走样。
- Windows PowerShell 5.1 与 7 的 profile 是两个文件，卸载时都扫；用户自定义到别处的 profile 不会被扫到（除宿主报告的那条）。

## 验证

单元测试（Linux 上可全跑）：

- `supportedShells` / `isSupportedShell` 的平台矩阵；`setup --shell powershell` 在非 Windows 退出码 2，`--shell fish` 在 win32（`PI_PRESETS_PLATFORM=win32`）退出码 2。
- `renderFunctionSource('powershell', ...)`：引号转义（路径含 `'`）、`@args` 透传、内容与写入 profile 的块逐字节一致。
- 假宿主端到端：在临时目录放可执行的 `pwsh.exe` / `powershell.exe`（带 shebang 的 shell 脚本）打印各自的 profile 路径，注入 PATH 后跑 `installShellIntegration` / `setup`，断言两个 profile 都被写入、目录被创建、BOM 与 CRLF 正确。
- profile 安装/卸载不变量：`install → remove` 逐字节还原；`install → install → remove`；`remove → install` 与单次 `install` 一致；不存在/空 profile；块后有用户内容；标记不完整整体中止（退出码 1，文件不变）。
- teardown 候选扫描：宿主不存在时仍能剥离推算路径与 `%OneDrive%` 路径上的块；无标记文件不被改写。
- 部分失败：两个假宿主里一个查询失败时，`setup` 退出码 1 且两个 profile 都未改动；`teardown` 仍剥离推算候选、退出码 0，stderr 带降级说明。
- 编码探测：UTF-16LE/BE BOM 的 profile 让 `install` 与 `remove` 都退出码 1 且文件逐字节不变；UTF-8 BOM 保留；无 BOM 按 UTF-8 往返。
- `quoteForCmd` 用例表：空串、空格、制表符、内嵌 `"`、尾部反斜杠、`&|<>^()` 无空格、已在引号内、非 ASCII、`%`/`!` 原样。
- `findRealPi` 在 win32 语义下：按 `PATHEXT` 顺序（注入 `.COM;.EXE;.BAT;.CMD`）、跳过无扩展名 `pi`、PATH 顺序优先、都找不到时报错。
- `install-presets`：注入 runner 断言 `npm_execpath` 分支用 `process.execPath`，win32 回退用 ComSpec。

真实冒烟（需要一台 Windows，本机跑不了，交付时明确告知）：

- `npm install && npm run setup` → 新开对应宿主 → `pi -ps coding` 进入 TUI；`pi -ps coding -p "list ts files"`；含空格与 `&` 的 prompt；`npm run teardown` 后 profile 逐字节还原。
- 在 pwsh 7 与 Windows PowerShell 5.1 里各跑一遍上面的流程（两个宿主的传参规则不同，只测一个不算过）。
- 仓库放在含中文的路径（`C:\Users\<中文>\pi-presets`）下重跑安装，并试一次 `--dry-run` 的 `Invoke-Expression` 用法。
